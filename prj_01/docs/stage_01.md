# Этап 1. Сбор и анализ требований

## 1. Предметная область и ключевые процессы

HR-система предприятия хранит данные о сотрудниках и кадровых событиях. Каждый сотрудник относится к отделу, занимает должность и (кроме руководителя верхнего уровня) подчиняется непосредственному руководителю, что образует иерархию подчинения. В системе фиксируются отпуска, больничные, а также процесс подбора персонала: вакансии, кандидаты, отклики и собеседования.

HR-менеджер работает с веб-интерфейсом, в котором должны отображаться:

- структура подчинения (кто кому подчиняется);
- количество отпусков по отделам;
- воронка подбора по вакансиям (сколько кандидатов дошло до каждого этапа).

### Ключевые процессы

| Процесс | Шаги | Что меняется в данных |
|---|---|---|
| Приём сотрудника | 1. Выбрать отдел и должность. 2. Указать руководителя. 3. Внести личные данные и дату приёма. 4. Присвоить статус «работает» | Новая запись сотрудника; связи с отделом, должностью и руководителем; дата приёма; статус |
| Перевод сотрудника (смена отдела, должности или руководителя) | 1. Выбрать сотрудника. 2. Указать новые отдел, должность или руководителя и дату перевода. 3. Проверить, что новый руководитель не является подчинённым сотрудника | Обновляются отдел, должность, руководитель; при необходимости сохраняется история назначений с датами |
| Увольнение | 1. Выбрать сотрудника. 2. Указать дату и причину. 3. Переназначить его подчинённых другому руководителю. 4. Сменить статус на «уволен» | Статус и дата увольнения; у подчинённых меняется руководитель; будущие отпуска отменяются |
| Оформление отпуска | 1. Сотрудник или HR создаёт заявку (даты, тип отпуска). 2. Проверка пересечений с другими отпусками и больничными. 3. Руководитель согласует или отклоняет. 4. После согласования отпуск утверждается | Новая запись отпуска со статусом (заявлен, согласован, отклонён, отменён, использован); даты начала и конца; кто согласовал |
| Оформление больничного | 1. Внести сотрудника и даты болезни. 2. Указать номер больничного листа. 3. Закрыть больничный в день выхода | Новая запись больничного; даты начала и конца; статус (открыт, закрыт) |
| Открытие вакансии | 1. Выбрать отдел и должность. 2. Указать количество мест, требования и дату открытия. 3. Статус «открыта» | Новая запись вакансии; связь с отделом и должностью; статус; дата открытия |
| Приём отклика кандидата | 1. Внести данные кандидата (или найти существующего). 2. Создать отклик на вакансию. 3. Установить начальный этап воронки | Запись кандидата; запись отклика (кандидат, вакансия, дата); текущий этап |
| Проведение собеседования | 1. Назначить дату, время и интервьюера. 2. Проверить, что интервьюер и кандидат не заняты. 3. Провести собеседование. 4. Внести результат и оценку | Запись собеседования (отклик, интервьюер, дата, тип, результат); этап отклика может смениться |
| Продвижение по воронке подбора | 1. По результату собеседования выбрать: перевести на следующий этап или отказать. 2. Зафиксировать новый этап и дату | История этапов отклика; текущий этап; причина отказа |
| Закрытие вакансии и найм | 1. Сделать кандидату оффер. 2. При принятии оффера создать сотрудника (процесс «Приём сотрудника»). 3. Закрыть вакансию, когда заполнены все места | Статус отклика «принят»; новая запись сотрудника; статус вакансии «закрыта»; дата закрытия |
| Построение отчётов для HR-менеджера | 1. Запросить дерево подчинения. 2. Запросить число отпусков по отделам за период. 3. Запросить воронку по вакансии | Данные не меняются (только чтение) |

### Ограничения

Типы ограничений:

- **Структурное** — целостность структуры и связей данных (внешние ключи, иерархия, уникальность).
- **Бизнес-правило** — требование предприятия или логики кадровых процессов, которое может меняться.
- **Техническое** — допустимые значения и формат данных (NOT NULL, CHECK, списки значений).

| Тип | Ограничение | Источник |
|---|---|---|
| Структурное | Каждый сотрудник относится ровно к одному отделу и занимает ровно одну должность на момент времени | Логика процесса |
| Структурное | Отпуск, больничный и собеседование должны быть связаны с существующим сотрудником (кандидатом) | Логика процесса |
| Структурное | Сотрудник не может быть собственным руководителем | Физическая реальность |
| Структурное | В иерархии подчинения не должно быть циклов (A подчиняется B, а B подчиняется A) | Логика процесса |
| Бизнес-правило | Руководитель верхнего уровня один, остальные сотрудники имеют руководителя | Бизнес-политика |
| Техническое | Дата окончания отпуска (больничного) не может быть раньше даты начала | Физическая реальность |
| Техническое | Дата увольнения не может быть раньше даты приёма | Физическая реальность |
| Бизнес-правило | Один сотрудник не может иметь два пересекающихся отпуска | Физическая реальность |
| Бизнес-правило | Отпуск не может пересекаться с больничным того же сотрудника | Бизнес-политика |
| Бизнес-правило | Один сотрудник (интервьюер) или кандидат не может участвовать в двух собеседованиях одновременно | Физическая реальность |
| Бизнес-правило | Дата собеседования не может быть раньше даты отклика | Логика процесса |
| Бизнес-правило | Количество дней отпуска в год не больше установленной нормы (например, 28 календарных дней основного отпуска) | Бизнес-политика |
| Техническое | Оценка собеседования лежит в допустимом диапазоне (например, от 1 до 5) | Бизнес-политика |
| Техническое | Количество мест в вакансии не меньше 1 | Логика процесса |
| Техническое | Допустимые значения статусов ограничены списком (сотрудник: работает, в отпуске, на больничном, уволен; отпуск: заявлен, согласован, отклонён, отменён, использован; вакансия: открыта, закрыта) | Логика процесса |
| Бизнес-правило | Уволенный сотрудник не может получать новые отпуска и больничные | Логика процесса |
| Бизнес-правило | Отклик на закрытую вакансию создать нельзя | Бизнес-политика |
| Структурное | Кандидат может откликнуться на одну и ту же вакансию только один раз | Логика процесса |
| Структурное | Табельный номер сотрудника уникален; e-mail сотрудника уникален | Логика процесса |
| Структурное | Название отдела уникально; номер больничного листа уникален | Логика процесса |
| Бизнес-правило | Этапы воронки идут в заданном порядке (отклик, скрининг, собеседование, оффер, найм); этап нельзя пропустить | Бизнес-политика |
| Бизнес-правило | Число принятых кандидатов не превышает число мест в вакансии | Логика процесса |
| Техническое | ФИО, дата приёма, отдел и должность сотрудника обязательны (NOT NULL) | Логика процесса |
| Бизнес-правило | Отпуск утверждает непосредственный руководитель сотрудника или HR | Бизнес-политика |

## 2. Роли пользователей

Роль — это набор прав и действий, доступных определённому типу пользователя. Роль не равна конкретному человеку: один человек может иметь несколько ролей (например, руководитель отдела одновременно является сотрудником и подаёт заявку на собственный отпуск).

Роль руководителя отдела определяется по данным (у сотрудника есть подчинённые), а роли HR-менеджера и администратора задаются полем «Роль в системе» таблицы «Сотрудник». Один человек имеет одно значение этого поля и дополнительно может быть руководителем.

| Роль | Действия | Какие данные доступны |
|---|---|---|
| Сотрудник | Просматривает свою карточку (отдел, должность, руководитель); подаёт заявку на отпуск; смотрит статус своих заявок и остаток дней отпуска; сообщает о больничном; видит своё место в структуре подчинения | Только свои данные: личная карточка, отпуска, больничные |
| Руководитель отдела | Согласует или отклоняет заявки на отпуск подчинённых; смотрит график отпусков и больничных своего отдела; видит структуру своего подразделения; участвует в собеседованиях как интервьюер и вносит оценку кандидата | Данные своих подчинённых и своего отдела; собеседования, где он интервьюер |
| HR-менеджер | Оформляет приём, перевод и увольнение сотрудников; ведёт отпуска и больничные; открывает и закрывает вакансии; ведёт кандидатов, назначает собеседования и двигает отклики по воронке; формирует отчёты (структура подчинения, отпуска по отделам, воронка подбора) | Данные всех сотрудников, отпусков, больничных, вакансий, кандидатов и собеседований |
| Администратор | Управляет справочниками (отделы, должности, типы отпусков, этапы воронки); создаёт учётные записи и назначает роли; настраивает нормы (например, дни отпуска в год); делает резервные копии и просматривает журнал действий | Справочники, учётные записи и роли; технические данные системы |

### Сотрудник

| Действие | Входные данные | Результат | Ограничения |
|---|---|---|---|
| Просмотр своей карточки | Идентификатор сотрудника (из учётной записи) | Отображены отдел, должность, руководитель, дата приёма | Видны только свои данные |
| Подача заявки на отпуск | Сотрудник, дата начала, дата окончания, тип отпуска | Создана заявка со статусом «заявлен» | Дата окончания не раньше даты начала; нет пересечений с другими отпусками и больничными; не превышена годовая норма дней |
| Отмена своей заявки | Номер заявки | Статус заявки «отменён» | Отменить можно только заявку в статусе «заявлен» или «согласован» до даты начала |
| Просмотр остатка отпуска | Сотрудник, год | Показано число использованных и оставшихся дней | Видны только свои данные |
| Сообщение о больничном | Сотрудник, дата начала, номер больничного листа | Создан больничный со статусом «открыт» | Номер листа уникален; нет пересечения с отпуском; сотрудник не уволен |

### Руководитель отдела

| Действие | Входные данные | Результат | Ограничения |
|---|---|---|---|
| Согласование заявки на отпуск | Номер заявки, решение (согласовать или отклонить), комментарий | Статус заявки «согласован» или «отклонён»; сохранён согласовавший | Заявка принадлежит его подчинённому; решение принимается только по заявке в статусе «заявлен» |
| Просмотр графика отпусков и больничных отдела | Отдел, период | Список отпусков и больничных подчинённых за период | Только сотрудники его отдела |
| Просмотр структуры подразделения | Руководитель (из учётной записи) | Дерево подчинённых | Только его ветка иерархии |
| Внесение результата собеседования | Номер собеседования, оценка, комментарий, решение | Сохранены результат и оценка; этап отклика может смениться | Он назначен интервьюером; оценка в допустимом диапазоне (1–5); собеседование уже проведено |

### HR-менеджер

| Действие | Входные данные | Результат | Ограничения |
|---|---|---|---|
| Приём сотрудника | ФИО, дата рождения, контакты, отдел, должность, руководитель, дата приёма | Создан сотрудник со статусом «работает» и табельным номером | Табельный номер и e-mail уникальны; ФИО, отдел, должность и дата приёма обязательны; руководитель существует |
| Перевод сотрудника | Сотрудник, новые отдел, должность или руководитель, дата перевода | Обновлены данные; сохранена история назначений | Новый руководитель не сам сотрудник и не его подчинённый (нет циклов) |
| Увольнение сотрудника | Сотрудник, дата увольнения, причина, новый руководитель для подчинённых | Статус «уволен»; подчинённые переназначены; будущие отпуска отменены | Дата увольнения не раньше даты приёма; у подчинённых должен остаться руководитель |
| Открытие вакансии | Отдел, должность, число мест, требования, дата открытия | Создана вакансия со статусом «открыта» | Число мест не меньше 1; отдел и должность существуют |
| Ввод кандидата и отклика | ФИО, контакты кандидата, вакансия, дата отклика | Созданы кандидат и отклик на первом этапе воронки | Один отклик кандидата на вакансию; вакансия открыта |
| Назначение собеседования | Отклик, интервьюер, дата и время, тип | Создано собеседование | Интервьюер и кандидат не заняты в это время; дата не раньше даты отклика |
| Перевод отклика по воронке | Отклик, новый этап или отказ, причина отказа | Обновлён этап; запись добавлена в историю этапов | Этапы идут по порядку, пропуск запрещён; принятых не больше числа мест |
| Построение отчётов | Тип отчёта (структура, отпуска по отделам, воронка), период, вакансия | Показаны дерево подчинения, число отпусков по отделам, количество кандидатов на каждом этапе | Только чтение; доступно HR-менеджеру |

### Администратор

| Действие | Входные данные | Результат | Ограничения |
|---|---|---|---|
| Управление отделами | Название отдела, родительский отдел (если есть) | Создан или изменён отдел | Название отдела уникально; удалить отдел с сотрудниками нельзя |
| Управление должностями | Название должности, описание | Создана или изменена должность | Название должности уникально; удалить используемую должность нельзя |
| Управление справочниками | Типы отпусков, этапы воронки, статусы | Обновлены справочники | Значения статусов из заданного списка; порядок этапов воронки сохраняется |
| Создание учётной записи и назначение роли | Сотрудник, логин, роль | Создана учётная запись с ролью | Логин уникален; учётная запись привязана к существующему сотруднику |
| Настройка норм | Годовая норма дней отпуска, диапазон оценок | Сохранены новые значения норм | Норма больше 0; новые значения не меняют уже утверждённые отпуска |
| Просмотр журнала действий | Период, пользователь | Список операций | Только чтение; записи журнала не изменяются и не удаляются |

## 3. Бизнес-правила

Бизнес-правило — это утверждение о том, что должно быть истинно в данных всегда. Не каждое правило можно выразить одним ограничением СУБД: некоторые требуют триггеров или логики приложения. СУБД на этом этапе ещё не выбрана, поэтому примеры реализации даны для PostgreSQL.

| № | Бизнес-правило | Категория | Где реализуется |
|---|---|---|---|
| Б1 | У одного сотрудника не может быть двух пересекающихся отпусков | Ограничение состояния | Ограничение EXCLUDE на (id_сотрудника, период отпуска) для неотменённых отпусков (PostgreSQL) или триггер |
| Б2 | Дата окончания отпуска (больничного) не может быть раньше даты начала | Ограничение домена | CHECK (дата_окончания >= дата_начала) |
| Б3 | Сотрудник не может быть собственным руководителем, и в иерархии подчинения не должно быть циклов | Ограничение структуры | CHECK (id_сотрудника <> id_руководителя) для первой части; для циклов триггер с рекурсивным запросом |
| Б4 | Табельный номер сотрудника уникален | Ограничение уникальности | UNIQUE (табельный_номер) |
| Б5 | Отпуск сотрудника не может пересекаться с его больничным | Ограничение состояния | Триггер (одно ограничение СУБД не может сравнивать две таблицы) |
| Б6 | Сумма дней отпуска сотрудника за год не может превышать установленную норму | Ограничение количества | Триггер или логика приложения |
| Б7 | Кандидат может откликнуться на одну вакансию только один раз | Ограничение уникальности | UNIQUE (id_кандидата, id_вакансии) |
| Б8 | Этапы воронки подбора проходятся по порядку, пропускать этап нельзя | Ограничение последовательности | Триггер или логика приложения (проверка порядка этапов по упорядоченному списку) |

## 4. Состав данных

## 5. Ожидаемые объёмы через 1 год

Допущения: предприятие среднего размера, около 500 сотрудников на старте; текучесть около 15% (≈75 приёмов и увольнений за год); около 60 открытых вакансий; около 40 откликов на вакансию; у каждого сотрудника в среднем 2 отпуска и 1–2 больничных в год. Уволенные сотрудники и закрытые вакансии остаются в базе.

|---|---|---|

| История назначений | ≈ 700 | по записи на сотрудника + около 100 переводов |
| Отпуск | ≈ 1 100 | 500 × 2 + отклонённые и отменённые заявки |
| Больничный | ≈ 750 | 500 × 1,5 |
| Вакансия | ≈ 60 | по допущению |
| Кандидат | ≈ 2 000 | часть кандидатов откликается на несколько вакансий |
| Отклик | ≈ 2 400 | 60 × 40 |
| История этапов отклика | ≈ 6 000 | в среднем 2–3 этапа на отклик |

Вывод: объёмы небольшие (самые большие таблицы — история этапов отклика и отклик), поэтому для выбранной СУБД производительность не будет проблемой, но индексы на внешних ключах и датах для отчётов всё равно понадобятся.

## 6. Частота операций

Частота операций определяет архитектуру: частое чтение требует индексов на поля поиска, частая запись — минимальных ограничений на путь записи, редкие тяжёлые отчёты можно выполнять в фоновом режиме. Оценки сделаны для предприятия примерно на 500 сотрудников (допущения из раздела 7.3).

| Процесс | Тип | Частота | Важность |
|---|---|---|---|
| Поиск сотрудника или кандидата (по ФИО, отделу, статусу) | Чтение (OLTP) | 100/день | Высокая — HR ждёт результат |
| Просмотр своей карточки сотрудником | Чтение (OLTP) | 100/день | Средняя |
| Просмотр своих отпусков и остатка дней | Чтение (OLTP) | 50/день | Средняя |
| Подача заявки на отпуск | Запись (OLTP) | 5/день | Высокая — проверка пересечений при вводе |
| Согласование заявки на отпуск | Обновление (OLTP) | 5/день | Средняя |
| Отмена заявки на отпуск | Обновление (OLTP) | 1/день | Низкая |
| Сообщение о больничном | Запись (OLTP) | 3/день | Средняя |
| График отпусков и больничных отдела (руководитель) | Чтение (OLTP) | 20/день | Средняя |
| Просмотр структуры подчинения | Чтение (рекурсивный запрос) | 20/день | Высокая — основной экран HR |
| Ввод кандидата и отклика | Запись (OLTP) | 10/день | Средняя |
| Назначение собеседования | Запись (OLTP) | 5/день | Высокая — проверка занятости |
| Внесение результата собеседования | Обновление (OLTP) | 5/день | Средняя |
| Перевод отклика по воронке | Обновление (OLTP) | 25/день | Средняя |
| Обновление статусов сотрудников (отпуск, больничный, выход) | Пакетная | 1/день (ночью) | Средняя |

| Открытие вакансии | Запись (OLTP) | 5/месяц | Низкая |
| Управление отделами и должностями | Запись | 5/месяц | Низкая |
| Ежегодный пересчёт остатков отпусков | Пакетная | 1/год | Низкая |

Вывод: самые частые операции — чтение и простые записи (поиск, просмотр данных, подача заявок, движение откликов по воронке). Редкие тяжёлые операции — отчёты и пакетные обновления, их можно запускать отдельно от основной работы.

## 7. Требования к производительности

Требование к производительности — это ожидаемое время ответа системы на конкретную операцию при заданной нагрузке. Эти требования определяют, какие индексы и стратегии хранения будут выбраны на этапе физического проектирования.

| № | Требование | Обоснование |
|---|---|---|
| П1 | Поиск сотрудника или кандидата по ФИО, отделу и статусу — не более 200 мс при 20 одновременных запросах | Самая частая операция, HR ждёт результат в реальном времени |
| П2 | Построение структуры подчинения (все сотрудники предприятия, до 1 000 записей) — не более 500 мс | Основной экран HR-менеджера; рекурсивный запрос по полю «руководитель» |
| П3 | Проверка пересечения нового отпуска с другими отпусками и больничными сотрудника — не более 50 мс | Выполняется при каждой заявке, критична для бизнес-правил Б1 и Б5 |
| П4 | Подача и согласование заявки на отпуск — не более 500 мс на одну операцию | Пользователь ждёт подтверждения, ошибки нужно показать сразу |
| П5 | Проверка занятости интервьюера и кандидата при назначении собеседования — не более 100 мс | Выполняется при каждом назначении, защищает от двойных собеседований |
| П6 | Отчёт «Отпуска по отделам» за год — не более 3 секунд при объёме до 10 000 записей об отпусках | Редкий запрос, может выполняться дольше, но не должен замедлять остальную работу |
| П7 | Отчёт «Воронка подбора по вакансии» — не более 2 секунд при объёме до 30 000 записей истории этапов | Строится по истории этапов, самой большой таблице; нужен HR для принятия решений |
| П8 | Просмотр сотрудником своих отпусков и остатка дней — не более 300 мс | Личный кабинет, частый доступ |
